cfamily.CheckedFunction

Section titled “cfamily.CheckedFunction”

A checked function: its node, name, parameters (with their types) and body.

cfamily.CheckedProgram

Section titled “cfamily.CheckedProgram”

A checked program: its functions, the statements that initialize the globals (in order, before main), and the tables checking built (running needs the types’ sizes), and the functions checked only if used (ProgramExtension.lazy) not checked yet, each with the globals before it.

cfamily.ProgramExtension

Section titled “cfamily.ProgramExtension”

How a dialect takes part in checking a program. Each has a default that leaves it to the core.

  • entry: the function a run starts at (main in C and C++; a board’s core names its own: ESP32’s app_main);
  • prepare: the dialect’s passes on the items before checking (none of the dialect’s items may be left that the core or the dialect’s other extensions do not check), given also the entry’s name and the types the type query puts in the program’s holes (they are used as much as the types the program writes: C++ brings in the library that declares them);
  • tables: what the dialect adds to the tables, from the items;
  • answer: the program’s items with what a request of checking needs added (none: the request cannot be met); the program is then prepared and checked again;
  • parameterType: how a parameter of a type is passed (C++ passes a class with a nontrivial copy by reference);
  • functionBody: a function’s checked body wrapped (C++: a noexcept function’s boundary);
  • effectFunctions: functions whose bodies the effect summaries also need (function templates);
  • instantiate: the definition of a function template’s instance by its name (f<int>), made from the template when a call deduces it and the program does not have it (checked as a deferred function, as Clang instantiates pending definitions at the end); none to ask for it instead (a request: the program prepared and checked again).

The first name defined twice among struct and union tags (they share one name space, C11 6.2.3).

cfamily.TypeSyntax.needsUndefined

Section titled “cfamily.TypeSyntax.needsUndefined”

Whether a member’s written type needs a struct or union not yet defined (not behind a pointer): a member’s type is complete (C11 6.7.2.1p3), and a struct is complete only after its closing brace (6.7.2.1p8).

The node of the first name repeated in the list.

cfamily.Program.enumerators

Section titled “cfamily.Program.enumerators”

The enumeration constants of an enum: without a value the previous plus one (the first is 0); a value is an integer constant expression; each fits int (C11 6.7.2.2p2).

cfamily.Program.enumerator

Section titled “cfamily.Program.enumerator”

One enumeration constant with its value, then the rest.

cfamily.Program.integerTypeOf

Section titled “cfamily.Program.integerTypeOf”

The integer type a written type is, if it is one.

cfamily.Program.constantOf

Section titled “cfamily.Program.constantOf”

A variable’s value as a constant, when the rules make const integral variables constants: a const integer type initialized with an integer constant, converted to the type.

cfamily.Program.typeNames

Section titled “cfamily.Program.typeNames”

The type names of the items, in order: typedefs (each once), enums (unsigned int if no constant is negative, else int, as clang), the constants (with const integral variables where the rules allow, Program.constantOf).

cfamily.ProgramDialect.parameterType

Section titled “cfamily.ProgramDialect.parameterType”

A parameter’s type: an array is adjusted to a pointer to its element (C11 6.7.6.3p7), then the dialect’s way of passing it.

The parameters of a function with their types, in order.

cfamily.ProgramDialect.resultType

Section titled “cfamily.ProgramDialect.resultType”

A function’s result type (none is void).

cfamily.ProgramDialect.defaultOf

Section titled “cfamily.ProgramDialect.defaultOf”

A parameter’s default argument checked in the scope of the globals: a constant if it needs nothing first, else evaluated at each call ([dcl.fct.default]p9).

cfamily.ProgramDialect.defaults

Section titled “cfamily.ProgramDialect.defaults”

The default arguments of the parameters, in order.

cfamily.ProgramDialect.signatureOf

Section titled “cfamily.ProgramDialect.signatureOf”

A function’s signature; its defaults checked in the tables g (none when withDefaults is false).

cfamily.ProgramDialect.signaturesFrom

Section titled “cfamily.ProgramDialect.signaturesFrom”

The signatures of the functions after those done (kept in reverse), in order: a loop over the functions (the library’s are hundreds), not one level of recursion per function.

cfamily.ProgramDialect.signatures

Section titled “cfamily.ProgramDialect.signatures”

The signatures of the functions, in order.

cfamily.ProgramDialect.globalTypes

Section titled “cfamily.ProgramDialect.globalTypes”

The globals with their declared types, the last first (the environment defaults are checked in: a default may use a global, read when the call is made, [dcl.fct.default]p9).

cfamily.ProgramDialect.signaturesInOrder

Section titled “cfamily.ProgramDialect.signaturesInOrder”

The signatures with their defaults, in order: a function’s defaults are checked with the functions before it having theirs (a default may call a function declared before it, whose own defaults apply, [dcl.fct.default]p9).

cfamily.Stmt.leadingLabels

The labels a statement starts with (a label’s statement may be a label too).

cfamily.Item.headersIncluded

The headers a program includes, as written.

cfamily.ProgramDialect.function

Section titled “cfamily.ProgramDialect.function”

Checks a function: its labels distinct, no jump past an initialization unless the rules allow it, the body with the parameters (then the globals) in scope.

cfamily.ProgramDialect.global

Section titled “cfamily.ProgramDialect.global”

A global’s declaration: its initializer a constant (no effects, reading no variable, C11 6.7.9p4; taking an address is fine), zero without one; where the rules allow dynamic initialization, whatever the declaration runs (a constructor, a call; C++ [basic.start.dynamic]).

cfamily.ProgramDialect.itemsFrom

Section titled “cfamily.ProgramDialect.itemsFrom”

The items in order: a global is visible to the items after it. What is checked so far is kept in reverse (in done) and put in order at the end: the check goes through the items as a loop, not one level of recursion per item (the program’s items with the library’s are hundreds, and a kernel evaluating it would nest that deep).

cfamily.ProgramDialect.items

Section titled “cfamily.ProgramDialect.items”

The items in order: a global is visible to the items after it.

cfamily.Item.globals

Section titled “cfamily.Item.globals”

The globals of the items with their written types (for the effect summaries).

cfamily.ProgramDialect.mainParameters

Section titled “cfamily.ProgramDialect.mainParameters”

Whether main’s parameters are none, or argc and argv (int, char **; C11 5.1.2.2.1p1).

cfamily.ProgramDialect.hasMain

Section titled “cfamily.ProgramDialect.hasMain”

Whether the program has int main(void) or int main(int argc, char *argv[]).

cfamily.ProgramDialect.hasEntry

Section titled “cfamily.ProgramDialect.hasEntry”

Whether the program has its entry: main as C and C++ require it, another (a board core’s app_main) as void f(void).

cfamily.ProgramDialect.missingEntry

Section titled “cfamily.ProgramDialect.missingEntry”

Why a program without its entry is rejected (another entry is the core’s: GCC’s linker names it).

cfamily.Program.addressedFunctions

Section titled “cfamily.Program.addressedFunctions”

The functions whose address the items take (f as a value), none when a member function’s address is taken (a call through a member pointer may call any member function).

cfamily.HoleTypes

Section titled “cfamily.HoleTypes”

The type query’s holes and the types they stand for (none in ordinary checking).

cfamily.ProgramDialect.effectsOf

Section titled “cfamily.ProgramDialect.effectsOf”

The effect summaries of the items’ functions (with the dialect’s own, like C++’s methods).

cfamily.ProgramDialect.withLibraryCode

Section titled “cfamily.ProgramDialect.withLibraryCode”

The items with the library’s C functions the program uses, checking the comparators whose calls change nothing a run shows (cfamily.librarycode); the summaries are computed only for a program that needs the library’s code.

cfamily.ProgramDialect.checkItems

Section titled “cfamily.ProgramDialect.checkItems”

Checks prepared items once: the tables, main, the items.

cfamily.FunctionDefinition.tag

Section titled “cfamily.FunctionDefinition.tag”

A function’s node and name.

cfamily.ProgramDialect.functionsChecked

Section titled “cfamily.ProgramDialect.functionsChecked”

Deferred functions checked, each with the globals before it.

cfamily.Reached

Section titled “cfamily.Reached”

A body checked, with where what it uses comes from: none for the program’s own (each use is its statement’s), else the node in the program a deferred function was first used at (what a library function uses is the program’s use).

cfamily.Reached.of

Section titled “cfamily.Reached.of”

A body reached from a node (none: the program’s own).

cfamily.Reached.uses

Section titled “cfamily.Reached.uses”

The functions a body uses, each with the node it counts as used at.

cfamily.CheckResult.placed

Section titled “cfamily.CheckResult.placed”

A rejection (or a construct the model does not provide) placed in the program: one at a node the program does not have (in a library’s function, checked because the program used it) is placed at the node it was used at.

cfamily.ProgramDialect.reachedChecked

Section titled “cfamily.ProgramDialect.reachedChecked”

Deferred functions checked, each with the node it was first used at (its rejection placed there).

cfamily.ProgramDialect.using

Section titled “cfamily.ProgramDialect.using”

A checked program with the deferred functions it uses checked (a dialect’s function checked only if used, ProgramExtension.lazy): those the bodies just checked call or take the address of, then those these do, until no more are used; one that does not check is the program’s failure.

cfamily.CheckedProgram.completed

Section titled “cfamily.CheckedProgram.completed”

A checked program with the deferred functions it uses checked.

cfamily.ProgramDialect.instanceRounds

Section titled “cfamily.ProgramDialect.instanceRounds”

How many rounds of instances’ definitions checking a program may take (an instance’s body may need another’s).

cfamily.ProgramDialect.newInstances

Section titled “cfamily.ProgramDialect.newInstances”

The instances the uses name that the program has no function or deferred function for, each made from its template once (ProgramExtension.instantiate), with the globals’ scope.

cfamily.ProgramDialect.checkAnswering

Section titled “cfamily.ProgramDialect.checkAnswering”

Checks a program: the dialect’s passes, the library’s C functions it uses, then the items; a request of the dialect is answered by adding items to the program, which is prepared and checked again (at most fuel times).

cfamily.ProgramDialect.requestFuel

Section titled “cfamily.ProgramDialect.requestFuel”

The number of times checking may start again for the dialect’s requests (each a function template’s instance or a lambda’s deduced result type in C++; a program with a few of each needs more than a dozen).

cfamily.Program.checkWith

Section titled “cfamily.Program.checkWith”

Checks a program with the type query’s holes or without: the dialect’s passes, the library’s C functions it uses, then the items.

cfamily.Program.check

Section titled “cfamily.Program.check”

Checks a program.

cfamily.Program.checkCollecting

Section titled “cfamily.Program.checkCollecting”

Checks a program for the type query: each hole stands for a value of the type given for it, and a statement that does not check is recorded (checkError) while checking goes on.
