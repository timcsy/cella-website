Cella language reference

This document describes every construct of Cella: how to write it and what it means. You can try it directly at cella-lang.org.

Every cella code block here is a complete file that can be checked. Section 1 shows the common forms on one page; the sections after it give the details.

1. On one page

Section titled “1. On one page”

The places where people most often go wrong:

What you may be used to How Cella writes it
a && b, a || b, !a a and b, a or b, not a
f x y, f(x)(y) f(x, y) (a call always has parentheses)
List<Int> List(Int)
fn def
class, impl Shape for Circle interface Shape { … }, implement Shape(Circle) { … }
{ ...p, x: 1 } p.with(x = 1)
Point { x: 0 } Point(x = 0)
|x| x + 1, fun x -> x + 1, x -> x + 1 x => x + 1
import a.{b, c} from a import b, c
"hello {name}" (meaning interpolation) f"hello {name}" (braces in a plain string are literal)
<T>, [T], {T} @given(T) above the definition
-- comment, /* comment */ // comment (there are no block comments)
x? let x = try e (see 11)
@external("js", "f") extern def (in this version the implementation goes by the name, see 9.2)

When you write one of these forms from another language, the error message says what to write instead.

2. Files and modules

Section titled “2. Files and modules”

A file is a module. The order is: mode (optional, see 10.3), import, declarations.

  • import m: use the public definitions of the module m without a prefix.
  • from m import a, b: take only a and b.
  • export * from m: files importing this one also see the names of m.
  • A module name can have dots, which are directories: import util.math is util/math.cella next to the entry file; import cpp.int is the submodule of the package cpp.
  • Common modules: std (natural numbers, booleans, lists, options and other basics), ordering.relations (the interfaces behind ==, < and other comparisons; in this version you import it yourself, and when it is missing the message says what to import), string (ToString, for f-strings), io (input and output), int (integers), fin (finite indices).
  • A library (the standard library and packages) names its definitions itself, wherever the file is: def cpp.add(…) is called cpp.add. A program’s definitions carry the module name (util.math.m).
  • Definitions are public by default; mark the ones only for this module private (see 3.5).

There are no namespace blocks: names carry their prefix (def IntegerType.divide(…)).

3. Definitions

Section titled “3. Definitions”

3.1 def

Section titled “3.1 def”
  • def name(parameters) -> Type { body }. A value without parameters is def name: Type = value; a value to compute is def name() -> Type { … }, called as name().
  • The return type is always written (-> T).
  • The last line of a body is its result; the lines before it name values with let.

3.2 Parameters and type parameters

Section titled “3.2 Parameters and type parameters”
  • A parameter is name: Type, separated by commas (also when each is on its own line).
  • @given(…) goes above the definition:
    • @given(A): a type parameter, which Cella infers at each call; @given(A, B) for several.
    • @given(n: Nat): a value that Cella infers.
    • @given(Monoid(A)), @given(d: Monoid(A)): an implementation of an interface (see 4.5); give it a name to refer to it in the body.
    • @given(u: Level) with Type(u): a universe level.
  • Using a name that was neither declared as a parameter nor in @given is an error.
  • @given is never written in the parameter list. Cella places each implicit parameter after the last explicit parameter it depends on.
  • When Cella cannot infer one, or to choose it, give it by name in the call, after the explicit arguments and in any order: twice(f, 3, A = Nat). A call with named arguments only (Point(x = 0)) builds a record.

When many definitions share the same premises, write a given { … } block:

  • A given { … } block lists one premise per line, without commas: A, n: Nat, A: Type(u), or an interface condition without a name, Combine(A). Every definition from the block to the end of the file can use them.
  • Each definition takes only the premises its type uses (the types of its parameters, its result type, its own @given, @shows; for a type, a record or an interface, the whole declaration), plus those their types use in turn (A: Type(u) brings u). An interface condition without a name comes along once every premise it is about is taken; one with a name comes along by its name. Above, twice and keep are as if they wrote @given(A, Combine(A)), and size takes nothing.
  • A premise used only in a body or a proof, and not in the type, is an error: write it into the type, or write an @given on that definition. Changing a proof never changes what it proves.
  • A definition’s own @given comes after the premises it takes. A name has one meaning: blocks add up, but a premise cannot be written twice; repeating a premise of a block in a definition’s @given, or naming a parameter or a definition like a premise, is an error.
  • The editor shows next to each definition the @given(…) it took. A premise only one definition needs is still written as @given.

3.3 Methods and self

Section titled “3.3 Methods and self”

A definition whose name has a prefix and whose first parameter is self is a method, called as x.f(…):

  • The type of self comes from the prefix (the self of Tree.size is Tree(A), with the parameter names of the type’s declaration); you can also write it, self: Tree(A).
  • x.f(a), where x has type T and T.f exists, is T.f(x, a): x goes to the first explicit parameter of T.f. It chains: x.size().toString(). The first explicit parameter of List.map is the function, so a list’s map is written map(f, xs). A record’s field comes first.

3.4 Local definitions: where

Section titled “3.4 Local definitions: where”
  • The definitions in where { def … } are only for this definition. They can recurse, call each other, and use the parameters of the outer definition (the start of count).
  • Mutually recursive top-level definitions need nothing: definitions in a module see each other (see 3.6).

3.5 private

Section titled “3.5 private”

Definitions are public by default; private makes one visible only in this module. It goes before def, fact, type, record and interface.

3.6 Mutual recursion

Section titled “3.6 Mutual recursion”

Definitions in a module see each other, so there is no mutual; Cella groups them by their references. Termination is checked as usual.

3.7 The order of the lines above a head

Section titled “3.7 The order of the lines above a head”

Several kinds of lines can stand above the head of a definition, in a fixed order (cella fmt puts them in it):

  1. Documentation ///
  2. Tool annotations: @cite, @steps, @simp, @infix, @model, @source, @derive, others
  3. @given
  4. @requires
  5. @ensures / @shows
  6. The head
  • @steps(N): the step limit for checking this definition (the default depends on the definition’s size; raise it when needed).
  • @simp: lets the simp() tactic use this equation. @irreducible and @reducible adjust unfolding.
  • @derive(C, D): above a type, generates implementations of interfaces (see 4.1).

4. Types

Section titled “4. Types”

4.1 type

Section titled “4.1 type”
  • type Name(parameters) { cases … }: one case per line (commas between cases on one line); a parameter without a type is a Type.
  • A case with data: node(left: Tree(A), value: A, right: Tree(A)). Field names: one field may go without a name (some(A)); two or more need names.
  • type Alias = T: gives a type another name.
  • @derive(DecEq, …) above a type generates implementations (below).
  • type has several cases; record is one shape.

Indexed types: each case gives its own result type, and the implicit parameters of a case stand above the case.

  • A case that is a path (a higher inductive type) is written loop: base =~= base (see 8).
  • Generated implementations: @derive(DecEq) gives the decision behind ==; @derive(Json) (with import json) gives T.toJson and T.fromJson.

4.2 record

Section titled “4.2 record”
  • record Name(parameters) { field: Type … }: one field per line, or commas on one line { x: Nat, y: Nat }.
  • Building: Point(x = 0, y = 0) (parentheses and =). Changing: p.with(y = 5) (gives a new value). Reading: p.x.
  • Each record is its own type: two records with a field of the same name do not get confused.
  • A record can declare a law it must satisfy: @shows(low <= high) with law ordered.

4.3 Pairs and named pairs

Section titled “4.3 Pairs and named pairs”
  • (A, B) is the type of pairs (three or more are (A, (B, C))), a value is (3, 4), and the parts are .first and .second.
  • Take a pair apart with the pattern (a, b) of a match.
  • When the type of the second part depends on the value of the first, name them: (n: Nat, p: P(n)); the value can be written (n: 1, p: …) too. The names of a value are for the reader: its parts match the parts of the type by position.

4.4 Infinite data: lazy record

Section titled “4.4 Infinite data: lazy record”
  • A lazy record is defined by what can be observed of it, and can be infinite; the checker infers its size. Read a field with s.head. The inferred size is an implicit parameter i; to choose it, give it by name: Stream(Nat, i = inf), tail(s, i = inf).
  • type and record are separate; lazy goes only on a record.
  • Building a value of a lazy record is not in this version (see 13).

4.5 interface and implement

Section titled “4.5 interface and implement”
  • interface Name(parameters) { members … }: fields empty: T, operation signatures combine(a: T, b: T) -> T, and the laws to satisfy. An operation can have a default, def f(x: T) -> T { … }.
  • implement Interface(Type) { member = implementation … }: combine(a, b) = a + b; a law is law name(parameters) by reason, as in a fact.
  • To name the implementation: implement Ord(Nat) as natLE { … }.
  • @given(T, Monoid(T)): T must have an implementation of Monoid, which Cella finds; to refer to it, @given(m: Monoid(T)).

4.6 Writing types

Section titled “4.6 Writing types”
  • A -> B: a function type; (A, B) -> C takes two arguments; taking one pair is ((A, B)) -> C.
  • (x: A) -> B(x): the result’s type depends on the argument. When the name is not used, write A -> B.
  • Type, Type(1): the type of types (a universe). For a level, @given(u: Level) with Type(u).
  • (e: T): a type annotation.
  • List(Int), Vec(A, n): a type applied to arguments is written like a call.

5. Expressions

Section titled “5. Expressions”

5.1 Calls and operators

Section titled “5.1 Calls and operators”
  • A call always has parentheses: f(x, y), List(Int); without arguments, f(). A method call is x.f(y) (see 3.3).
  • Operators are a fixed set (you cannot add new symbols):
Precedence (loosest to tightest) Operators
loosest x => e (lambda), A -> B
or
and
not
===, =~=, ==, !=, <, <=, >, >=
a word b (an English word declared @infix)
+, -
*, /, %
-x (unary minus)
tightest calls, .
  • Logic is the words and, or, not; == is the Boolean comparison (!= its negation), === the statement of equality, and =~= a path (see 6.1).
  • Operators are overloaded through interfaces: + is Add, - is Subtract (Negate in front of a value), * is Multiply, / is Divide, % is Modulo (import operators); <= is LE, < is LessThan, == is decided by DecCEq (import ordering.relations).
  • Write implement Add(Money) { add(a, b) = …, law addAssoc(a, b, c) by … } and + works on your type, and the type can be passed to functions with @given(T, Add(T)). Add and Multiply carry an associativity law that the implement proves; the other four have no law (a - b + b === a already fails for Nat).
  • If you do not want to prove the law, or the operation is not associative, define def Money.add(a: Money, b: Money) -> Money (likewise sub, mul, div, mod, neg): + looks for it first, but such a type cannot be passed to functions with @given(T, Add(T)).
  • Lists join with xs + ys (import operators), which is associative; append(xs, ys) is the same thing.
  • After import operators, a bare add(a, b) has two meanings (Nat.add and the interface’s operation) and is reported as ambiguous: write the full name, Nat.add or Add.add. The operators are not affected.
  • Comparisons chain: 0 <= b < width (each part is compared).
  • English words between their arguments: mark the definition @infix, and write a xor b. For example, def xor(a: Bool, b: Bool) -> Bool { … } marked @infix makes a xor b == false read as xor(a, b) == false. The definition must have exactly two explicit parameters; a name that is not marked @infix cannot stand between two operands, and the message says to mark it. A use earlier in the same file counts, and so does an imported word.

The rules for an @infix word: mixing it with a comparison needs no parentheses (comparisons come last); mixing it with arithmetic or to always needs them; the same word chained is left-associative; two different words mixed need parentheses. The word stands on one line with both of its sides.

5.2 lambda

Section titled “5.2 lambda”
  • x => e; several parameters (a, b) => e; with a type (x: Nat) => e.
  • For several lines on the right of =>, write a braces block, whose last line is the result.
  • Parameter types can be left out when they follow from the expected type.

5.3 let

Section titled “5.3 let”
  • let name = value, let name: Type = value; each let line of a block binds in order, and the last line is the result.

5.4 if

Section titled “5.4 if”

if condition { value } else { value } is an expression and both branches are required; the condition is a Bool. Write several lines inside the braces. After if the condition comes, then only {.

5.5 match

Section titled “5.5 match”
  • match value { pattern => result … }: one arm per line (commas on one line); several lines in an arm are => { … }.
  • Patterns: a name (binds), _, a constructor with sub-patterns node(l, _, r), a number, k + 1, a pair (a, b), lists [] and [x, ...rest].
  • Constructors need no type prefix (after import, they resolve by type); when names collide write Vec.empty, or from m import empty. A lone lower-case name is a new variable; the checker reports it and suggests a fix when a constructor of that name exists.
  • Several values at once: match (a, b) { (x, y) => … }.
  • In a match on an expression, the expression is replaced by the constructor in each arm.
  • To give the target type explicitly: match n returning (m => Vec(Nat, m)) { … }.
  • An impossible case calls an eliminator: i.impossible(); there is no new syntax for it (Fin(0) has no values).

5.6 Lists

Section titled “5.6 Lists”

[a, b, c]; when an item stands on its own line each item takes a comma, the last one too. Patterns [], [x, ...rest] are above.

5.7 Strings and literals

Section titled “5.7 Strings and literals”
  • Natural numbers: 0, 42, 1_000_000 (underscores only separate), 0xFF, 0b101; very large numbers work too. Negative: -3.
  • "…": a plain string, on one line; escapes \n \t \r \" \\. Braces are literal (when the name inside is in scope, the checker reminds you to write f"…" for interpolation).
  • f"…{e}…": interpolation; {e} is converted by ToString; {{ and }} are literal braces.

5.8 Holes to fill in later

Section titled “5.8 Holes to fill in later”

todo("what is left") or todo() marks a place to write later. A definition with a todo cannot be Accept; the check lists its type and context. _ is a part for Cella to infer.

5.9 Line breaks and commas

Section titled “5.9 Line breaks and commas”

Commas on one line; for line breaks the rule depends on the bracket:

Where With a line break
Parameters, arguments, tuples in ( ); lists in [ ] every item takes a comma, the last one too (a trailing comma)
Blocks, cases, fields and match arms in { } a line break is enough, no comma; commas only between items on one line
  • Continuing a line: a line that starts with a token that can only follow (===, ==, <=, +, ., ->, else, by) continues the previous line.
  • A line starting with - is a unary minus and does not continue; cella fmt breaks long expressions after the operator.
  • Liberal in what it reads: the parser accepts a comma more or less at a line break, and cella fmt prints the standard form above.
  • A line break after an operator or inside parentheses needs nothing special; only a { } block separates statements by lines.

5.10 Node labels

Section titled “5.10 Node labels”

@node("label") e marks e with the name of a node of the tool that wrote the program: the errors, holes and unknowns of cella check --json and cella holes --json carry the innermost label around them (the "node" field). A label is transparent: the meaning is that of e. It covers what the operand of unary - covers: @node("a") x + 1 labels x only.

6. Proofs

Section titled “6. Proofs”

6.1 Equality

Section titled “6.1 Equality”

Three forms, one meaning each:

Form Meaning Type
a == b the Boolean comparison, decided by DecCEq Bool
a === b the statement that a equals b (the type of proofs that they are equal, Eq of the identity module) a type
a =~= b a path from a to b (see 8) a type
  • A proof of === is refl (the two sides compute to the same), or comes from a lemma or tactics; by compute has the kernel compute whether the two sides are the same. It never touches a path, so a mode core file can use it.
  • Methods of h: a === b: h.sym() reverses it, h.trans(k) chains it, h.cong(f) applies f to both sides.
  • == needs an instance of DecCEq for the type. It carries two laws (decided true means equal, equal means decided true, both with ===), so the decision agrees with the statement; Nat, Int and String have instances, and your own type gets one with implement DecCEq(T). A type without one is an error that names the instance it needs.
  • == in a type position is an error whose message says to write ===; === where a Boolean is wanted is an error too (it is a statement).
  • (a == b) == true is an error: drop == true.
  • a != b is not (a == b); the negation of the equality is (a === b) -> Empty.

6.2 fact and @shows

Section titled “6.2 fact and @shows”
  • The @shows(…) above fact name(parameters) is the statement to prove. A fact without @shows is an error.
  • The body is by compute, by lemma(…), by { tactics }, or a block (two columns, a match).
  • Asserting a verdict: @shows(…) with fact name by compute is computed by the kernel; the other way is test (not in this version).

6.3 Two columns

Section titled “6.3 Two columns”

The expression on the left, the reason on the right; after the first line each line starts with ===:

  • Each step is === next expression by reason. The reason is a call of a lemma, compute or { tactics }. In a two-column proof of a path every step is =~=; one proof does not mix the two.
  • Applying a function to both sides of a step: .cong(f), as in by addZero(k).cong(n => n + 1).

6.4 Tactics: by { … }

Section titled “6.4 Tactics: by { … }”

In by { … } there is one step per line, each written like a call (with () even without arguments), and no ;.

Tactic Meaning
intro(), intro(x), intro(x, y) move an assumption or parameter into the context
exact(e), apply(f) use this term (or function)
rfl() the two sides are equal
induction(n), cases(n) split on n
rewrite(p), rewrite(p, reverse = true), rewrite(p, at = h) rewrite with an equation
simp(), simp(a, b), simp(only = [a, b]) simplify with @simp equations
ring(), omega(), linarith(), polyrith(), norm_num() arithmetic (import the module of each)
decide() decide by computation
linsolve(), linsolve([u1, u2]), linsolve([u1, u2], ["r1", "r2"]) solve a linear system (needs import linsys; the lists name the unknowns and the equations, which the verdict uses to say what is missing)
constructor(), left(), right(), exfalso(), contradiction() logic
try t, repeat(t), first(t1, t2), all(t) combine tactics
let h: T = proof prove a fact on the way
unfold(f), change(T), generalize(e, x), specialize(h, e), suffices(h, T), revert(x), clear(x) arrange the goal

6.5 A condition with its proof

Section titled “6.5 A condition with its proof”

if a == b as h { … } else { … }: the condition is the Boolean comparison, and h: a === b can be used in the first branch (it comes from the laws of DecCEq).

The other form is match decide(a === b) { yes(h) => …, no(h) => … } (with import decidable), whose no branch carries a proof too ((a === b) -> Empty).

7. Termination

Section titled “7. Termination”

Recursion must be structural by default (on a subterm of a parameter; lexicographic orders and mutual recursion are found automatically). A recursion that is not on a subterm needs a measure, which has no way to be written in this version yet (see 13).

8. Paths and cubical

Section titled “8. Paths and cubical”

Cella’s core is cubical type theory (CCHM). A path is a function on the interval:

  • path i => …: a path (path is a keyword only here). The point at i: p.at(i); 1 - i reverses it.
  • a =~= b is the path type. It needs mode cubical (or no declared mode); Eq.toPath(h) turns h: a === b into a path.
  • transport(x, along = line), transport(x, along = line, fixedWhen = i == 0): transport along a line of types.
  • compose(base = b, sides = { i == 0: path j => u, i == 1: path j => v }): the keys of sides are conditions.
  • a =~= b over (i => A(i)): a path between different types.
  • univalence(e): a path from an equivalence of types (e: Equiv(A, B)).
  • Glue(A, …), Sub(A, φ, u): ordinary calls.

Higher inductive types: a case whose type is a path.

An arm for a path case must be a path between the images of its endpoints, which Cella checks.

9.2 extern def

Section titled “9.2 extern def”
  • extern def is provided by the host; it can run (assume cannot). The verdict lists it as an “external function” assumption.
  • The result must be IO(R) or IO(Either(String, R)); R and each parameter are a Nat, a Bool, Unit, a String, or a List, an Option or a pair of them.
  • In this version the implementation goes by the definition’s full name. Saying where it is with @source(js = "host_write", native = "host_write", wit = "cos-mos:device/device@0.1.0#pin-write") (keys registered by domain packages) is not in this version; see 13.
  • @ensures(…): a condition on the result, checked at run time (a value from the host that does not pass makes the program get a failure; it is not an axiom).

9.3 Models

Section titled “9.3 Models”

@model above a definition says it is an empirical model from outside the formal world (a source with an internal resistance, say). A rating linsolve finds under it is a bounded pass: the verdict lists the model’s name and hash among the assumptions.

10. Usage counts, modalities, modes

Section titled “10. Usage counts, modalities, modes”

10.1 Grades

Section titled “10.1 Grades”

A grade stands before the parameter name: ghost (erased: only in types), once (exactly once), many (any number of times, the default).

In a function type, a parameter with a grade always has a name: (once file: File) -> Unit.

Your own grades: type Budget { … } with implement Grades(Budget) { … } (the semiring rules are laws), enabled by mode careful extends core { grades = Budget } (see 10.3).

10.2 Modalities

Section titled “10.2 Modalities”
  • modality name from m to n: declares a modality. name(B) is the modal type; name.of(a) puts a value under the modality (a is checked under the lock), and the pattern name.of(x) of a match takes it apart.
  • A modality name stands before a parameter name: def back(sharp x: B), the same place as a grade.

10.3 mode

Section titled “10.3 mode”

A mode decides which features a definition may use:

  • The default is core, which is not written. Other modes are on the first line of the file, mode name (mode cubical for paths and higher inductive types, mode runtime for IO and foreign calls).
  • For one definition: @mode(core) above it.
  • Your own: mode careful extends core { grades = Budget }.

11. Programs that run

Section titled “11. Programs that run”

A file with main: IO(Unit) (or def main() -> IO(Unit)) can run.

  • In a function whose return type is a monad (IO, Option, Either(E), your own type that implements Monad), let x = try e takes the result of e, and the block fails when it fails; a line try e runs it and drops the result; the last line is the value of the block.

For your own type, write implement Monad(Chk) { pure(a) = …, bind(m, f) = … }.

12. cella fmt and cella migrate

Section titled “12. cella fmt and cella migrate”
  • cella fmt file… formats in place; cella fmt --check file… changes nothing, lists what would change and exits non-zero.
  • There is one standard format: width 100; function bodies always on their own lines; short type bodies on one line when they fit; => of match arms, ( of cases and : of record fields aligned within a block.
  • cella migrate <paths…> converts files in the old syntax to this one; a file is written back only when the core terms of every definition are the same.

13. Not in this version

Section titled “13. Not in this version”

These parse and format normally, and checking gives the message “not yet available in this version: …”: var, for, while, break, continue, return, ranges with to, assert, dictionaries, indexing a[i], test blocks, try outside let x = try e and a line of its own, literals whose type comes from the expected type (Int32(3); def x: Int = 1 is written Int.pos(1), and x + 1 is written x + Int.pos(1)), inferring universe levels, @requires / @ensures on definitions with a body, named @requires, and @source.

Also not in this version: an automatically loaded prelude (comparisons such as == and < need import ordering.relations), a measure for termination, declaring new SProp types, building values of a lazy record, and named arguments to ordinary functions (f(fuel = 100000); the named forms of Point(x = 0), transport and compose work).

Appendix: keywords

Section titled “Appendix: keywords”

These words are keywords only at the start of a declaration or in their position; elsewhere they are ordinary names (let path = "a", Bits.and(w, a, b)):

  • Declarations: given, def, fact, type, record, lazy, interface, implement, assume, extern, test, mode, extends, modality, where, import, from, export, as, private, law
  • Expressions: let, var, if, else, match, returning, for, while, in, return, break, continue, try, assert, by, path, over, to, and, or, not, unchecked
  • Annotations (starting with @): @given, @requires, @ensures, @shows, @invariant, @decreases, @computes, @cite, @steps, @simp, @infix, @model, @source, @derive, @mode
  • Grades: ghost, once, many

The part after a dot can be any of these words (v.end, p.path).
