Type theories

Cella’s core is cubical type theory (CCHM). On top of it, the same language has quantities (QTT), modalities (MTT), definitional proof irrelevance (SProp) and user-declared rewrite rules. You do not switch languages to use them: each one is a few keywords, and a definition’s mode says which of them it may use.

Every example on this page is checked by Cella when the site is built.

At a glance

Section titled “At a glance”
Theory What it gives you How you write it Checked by
Cubical (CCHM) paths as functions on an interval, function extensionality, univalence, higher inductive types a =~= b, path i => ..., transport, univalence, a case c: a =~= b both kernels
Higher inductive types types with path cases: circle, suspension, truncation, sphere, torus, pushout, join a case whose type is a path both kernels
Quantities (QTT) erased (ghost) and linear (once) parameters; your own semiring of usages ghost x: A, once x: A, implement Grades(G) {...} both kernels
Modalities (MTT) modal types and locks, with your own modalities and laws between them modality mu from m to n, mu(A), mu x: A both kernels
SProp propositions whose proofs are all definitionally equal SProp (declaring new types is not in this version) both kernels
Rewrite rules new computation rules for assumed constants assume def, @computes(...) with assume rule both kernels
Modes which of the above a definition may use @mode(core), mode X extends ... { grades = ... } both kernels (the runtime axis: elaborator)

“Both kernels” means the rule is checked twice, by the kernel and by an independent checker written from scratch from the same typing rules; a definition is accepted only if both agree.

Cubical type theory

Section titled “Cubical type theory”

A path a =~= b is a function from the interval to the type, with the endpoints fixed. You write it with path i => ... and use it with p.at(i); 1 - i reverses it. The equality a === b that @shows states is the inductive one, which needs no cubical machinery; Eq.toPath(h) turns it into a path.

funext is one line because a path is a function: function extensionality is not an axiom here, it computes.

Univalence. univalence turns an equivalence of types into a path between them, and transporting along it applies the equivalence. The standard library’s notEquiv is the equivalence Bool -> Bool given by not:

by compute is enough: the transport computes to not(true). The other primitives (transport with fixedWhen, compose, Glue, unglue) are available too; import foundations, path and equiv build the usual library on them.

Higher inductive types

Section titled “Higher inductive types”

A case whose type is a path is a path case. Matching on such a type needs an arm for it, and that arm must be a path between the images of its endpoints; Cella checks it.

flip sends north to south, so the meridian must be reversed. Writing merid(a) => path i => merid(a).at(i) instead is rejected, with the error at the arm: the path starts at north, but the type asks for south.

Path cases can have parameters (merid(a: A)) and can be paths between paths. The standard library’s hits module has the circle, suspension, propositional truncation, the interval, the torus, the 2-sphere, pushouts and joins, with their eliminators; winding computes the winding number of a loop on the circle through the universal cover (built with univalence):

Quantities (QTT)

Section titled “Quantities (QTT)”

A parameter can say how many times it may be used: ghost (erased: only in types, gone at run time), once (exactly once), or nothing (any number of times).

def twice(once x: Nat) -> Nat { x + x } is rejected: the linear x is passed to a parameter of add that may use it any number of times. An erased parameter can be used in types and in other erased positions, never in a value at run time. Erasure is not irrelevance: an erased argument is still compared like any other. For proofs that are all equal, use SProp, below.

Your own semiring. Besides ghost, once and many (any number of times), usages can come from a finite semiring you define: a type of elements and an implement Grades(G) giving its add, mul and order. Cella checks the semiring laws by computing them, then checks every use against it (through calls and recursive definitions too). A mode decides which usages its definitions may write: mode careful extends core { grades = G }.

Modalities (MTT)

Section titled “Modalities (MTT)”

A modality from mode m to mode n is declared with modality mu from m to n. mu(A) is the modal type, mu.of(a) puts a value under the modality (checking a under the lock mu), and a parameter mu x: A carries the modality.

Under a lock you cannot use outside variables that do not carry the modality, which is how a modality controls what may flow where. This follows Gratzer, Kavvos, Nuyts and Birkedal’s MTT.

SProp: definitional proof irrelevance

Section titled “SProp: definitional proof irrelevance”

A type declared in SProp is a proposition whose proofs are all definitionally equal, so nothing ever depends on which proof you have. A proof in SProp can only be taken apart to build another proof (the empty type is the exception: it eliminates into anything); a type in SProp has no path cases, and SProp is predicative. This is the system of Gilbert, Cockx, Sozeau and Tabareau (POPL 2019), as in Agda’s --prop. Declaring new SProp types has no syntax yet in this version.

Rewrite rules

Section titled “Rewrite rules”

An assume def introduces a constant without a definition; an assume rule gives it a computation rule, which both kernels use from then on:

The left side of a rule is a pattern; rules that overlap must agree, and a definition that relies on an assumption says so in its verdict.

Modes

Section titled “Modes”

A mode is a set of features. core has none of the above, cubical adds paths and higher inductive types, and runtime adds IO and foreign calls; mode X extends ... declares your own, with the usages it allows. A definition declared in a mode may use only what the mode admits, directly or through anything it depends on.

Declaring same in core is rejected: it uses a path, which needs cubical. A definition without a mode is not restricted. Modes are related only by inclusion (core is inside cubical and inside runtime), so you pay only for what you use, and a proof in core stays valid for a reader whose checker has no cubical machinery.

Also in the language

Section titled “Also in the language”
  • Infinite data (lazy record), with guarded recursion and productivity checking.
  • Universe levels (Type(u)) and cumulativity; sized types for termination.
  • The full rules, each with cases that must be accepted and cases that must be rejected, are in the typing rules that both kernels are written from.
